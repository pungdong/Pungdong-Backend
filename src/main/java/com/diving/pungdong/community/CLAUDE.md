# CLAUDE.md — community (커뮤니티)

이 패키지를 열면 자동 로드되는 좁은 컨텍스트. 전체 컨벤션은 루트 [CLAUDE.md](../../../../../../../CLAUDE.md).

> **package-by-feature.** `branding`(게시물 엔티티·프로필) · `account` · `course` 를 **단방향 참조**한다 —
> 그쪽은 이 패키지를 모른다.

> **게시물의 두 표면(커뮤니티 피드 ↔ 브랜딩 그리드) 관계 규칙은
> [docs/features/post-surfaces.md](../../../../../../../docs/features/post-surfaces.md) 가 단일 출처다.**
> 이 테이블을 읽거나 쓰는 코드를 건드리기 전에 읽을 것 — 한쪽 도메인만 보고 고쳐서 사고가 세 번 났다.

## 가장 먼저 알아야 할 것 — 게시물 테이블은 새로 만들지 않았다

**커뮤니티 포스트 = `branding.BrandingPost` 다.** 별도 테이블이 아니다.

- 브랜딩 게시물(V17)이 이미 미디어·태그 자식 테이블, 연결 강의, 숨김, 고정, UTC 타임스탬프를 갖고 있었고
  없는 건 카테고리·제목·노출 플래그뿐이었다.
- `account_branding` 은 계정당 1행(UNIQUE)이고 글의 작성자는 1명이라 **"글 ↔ 브랜딩 페이지" 는 항상 0..1**
  이다. 맵핑 테이블을 두면 모든 글에 0행 또는 1행이 생긴다 — 조인만 하나 늘어난 boolean 이다.
- 두 테이블로 나눴다면 브랜딩 그리드가 **UNION** 이 되어 정렬·페이징·`totalElements` 가 전부 얹히고,
  좋아요·댓글·신고가 **폴리모픽 FK**(DB 제약 불가)로 빠졌다.

**모든 글은 커뮤니티 글이고, 프로필에도 남길지만 고른다** (2026-08-18 작성 폼 통합).

| 상태 | 커뮤니티 피드 | 브랜딩 그리드 |
|---|---|---|
| `showOnProfile=false` (기본) | ✅ | ❌ |
| `showOnProfile=true` | ✅ | ✅ (= 예전 "브랜딩 글") |
| `isHidden=true` (둘 중 무엇이든) | ❌ | ❌ — 오너에게만 남는다 |

- 작성·수정은 `POST|PUT /community/posts` **하나**. 구 `POST /branding/me/posts` 는 구버전 앱 호환용이고
  거기로 온 글은 `showOnProfile=true` 로 고정된다. 여기 필드를 더하기 전에 **통합 폼으로 되는지 먼저 볼 것.**
- `showOnProfile` 은 요청의 **스냅샷**이다(미디어·태그와 같은 규칙) — PUT 에서 빠지면 false 로 읽혀 프로필에서
  내려간다. 사진 0장이면 켤 수 없다(그리드는 사진 타일).
- **숨김은 전역 스위치이고 경로도 하나**(`PATCH /community/posts/{id}/visibility`). 브랜딩 쪽 쌍둥이
  엔드포인트는 삭제했다 — 프로필 글만 통과시켜 커뮤니티 전용 글을 못 숨겼고, 어드민 조치 확인이 없어
  **신고로 내려간 글을 작성자가 되살리는 우회로**였다.
- `showInFeed` 는 이제 항상 1 이다(V31 에서 남은 0 행도 올렸다). 컬럼은 인덱스 선두 컬럼이라 남긴다.

## 이 도메인에서 자주 틀리는 것

1. **테이블·클래스 이름이 `branding_post` / `BrandingPost` 인 게 실수가 아니다.** ECS 롤링 배포 중에는
   구버전 태스크가 살아 있어서, 신버전이 부팅하며 RENAME 을 돌리면 그 태스크가 없는 테이블을 조회해
   **브랜딩 페이지가 500** 이 된다. 이름은 내부 구현이고 API 경로가 계약이라 바꿔서 얻는 게 없다.
   정리하려면 트래픽 없는 시점에 테이블·클래스를 함께 바꾸는 별도 PR 로.
2. **`category`·`title` 은 둘 다 NOT NULL(V31) 이고 두 쓰기 경로 모두 필수로 받는다.**
   기존 행은 `TOUR` / `'브랜딩 게시물'` 로 backfill 했다 — 없으면 수정하려는 작성자가 없던
   분류·제목을 발명해야 한다. (실사용자 데이터가 아니라서 backfill 이 가능했다: prod 최종 배포에는
   이 테이블 자체가 없다.) 구 브랜딩 경로에서 두 키를 빼면 예전엔 **조용히 지워졌지만** 이제 400 이다.
3. **카운터를 저장하지 않는다.** 좋아요·북마크·댓글 수는 각 테이블에서 집계한다. 피드 한 페이지에 대해
   **id 를 모아 group by 한 번** — 카드마다 세면 페이지 크기만큼 쿼리가 나간다(브랜딩 그리드가 미디어를
   일괄 조회하는 것과 같은 패턴). 역정규화 카운터는 review 도메인의 통계 갱신 버그를 물려받는 길이다.
   **인기 태그·지금 뜨는 토픽도 같다 — 집계 테이블을 만들지 말 것.** 태그는 색인된 자식 행이라
   `group by` 로 세지고, 카운터를 두면 작성·수정·삭제·숨김·어드민 조치 **5개 경로**와 동기화가 어긋난다.
4. **마커 테이블의 UNIQUE 가 멱등성의 근거다.** `(post, account)` UNIQUE 덕에 `POST` 를 두 번 보내도
   좋아요는 하나다. 레거시 `lecture_mark` 에는 이 제약이 없어 중복 찜이 가능하다 — 베끼지 말 것.
5. **댓글만 soft delete, 게시물은 hard delete + 숨김.** 반대로 하지 말 것. 대댓글이 달린 부모를 물리
   삭제하면 스레드가 끊긴다. 댓글 수 집계에서는 삭제된 것을 **빼야** 한다 — "댓글 3" 인데 2개만 보이면 버그다.
6. **대댓글은 1단까지.** `parent` 는 최상위 댓글만 가리킬 수 있고, DB 로 표현할 수 없어 서비스가
   `parent.isTopLevel()` 로 강제한다.
7. **정렬은 서버가 고정한다.** 클라이언트 `sort` 를 `Pageable` 에 태우지 않는다. 피드는 화이트리스트
   enum(`LATEST`·`POPULAR`), 댓글은 `createdAt ASC` 고정(파라미터 없음), size 상한 50.
   **`?category=MATCH` 는 자동으로 `meetDate ASC`** 다 — 디자인이 "같이가요는 일정 임박순 기본"이라
   명시했는데 그 정렬 pill 이 있는 화면이 Phase 1 범위 밖이라, 값을 enum 에 남기지 않고 기본값으로 살렸다.
8. **`MATCH` 글에는 강의를 연결할 수 없다.** 같이가요 영리활동 금지 가드 중 **기계적으로 강제 가능한
   부분**이다. 본문 광고 판정은 하지 않는다(오탐이 크다) — 그쪽은 `ReportReason.COMMERCIAL` 신고 →
   어드민 처리 경로로 간다.
9. **강의 연결은 강사만.** 일반 유저가 `linkedCourseId` 를 보내면 400. 내 코스가 아니어도 400.
   DRAFT·삭제된 코스는 **공개 응답에서 키 자체를 생략**한다(비공개 코스가 공개 화면에 새지 않게).
   ⚠️ **단 오너 본인의 상세에는 DRAFT 도 싣는다**(`toLinkedCourseForOwner`). 오너에게까지 감췄더니
   수정 폼이 `linkedCourseId` 를 프리필하지 못해 **스냅샷 교체로 연결이 조용히 끊겼다** — 요청에서
   "사용자가 뗐다" 와 구별되지 않아 클라이언트가 방어할 수도 없다. **카드는 예외 없음**(오너 개념이 없다).
10. **`mediaUrls` 는 우리 CDN base 검증을 통과해야 한다.** 브랜딩과 같은 규칙 — 없으면 본문에 임의
    외부 이미지를 심을 수 있고 삭제 로직이 남의 도메인을 지우려 든다.
11. **참여 신청 기능은 없고, 앞으로도 만들지 않는다.** 사용자 의도가 "신청류 = 기존 수강신청(예약)
    플로우" 라, 향후 버디 참여도 커스텀 참여 테이블이 아니라 **예약 플로우 통합**으로 설계한다.
    그래서 `capacity` 는 있지만 참여자 테이블도 `joinedCount` 도 없다 — 클라이언트는 "N명 모집" 으로 렌더한다.
12. **`boolean isX` 는 Jackson 이 `x` 로 직렬화한다.** 그런데 `@JsonProperty` 만 붙이는 건 해결이
    아니다 — 원시 `boolean isInstructor` 는 Lombok 게터가 `isInstructor()` 라 Jackson 이 이걸
    프로퍼티 `instructor` 로 보고, 필드의 `@JsonProperty("isInstructor")` 와 **키가 둘로 늘어난다.**
    **필드명에서 `is` 를 뗀다**(`private boolean instructor` + `@JsonProperty("isInstructor")`).
    `CommunityAuthorResponse` 가 그 형태다. (브랜딩 공개 프로필이 실제로 두 키를 내보내고 있었다.)
13. **게시물의 자식 행은 서비스가 지우지 않는다 — FK 가 `ON DELETE CASCADE` 다.** 글을 지우는 문이
    **둘**(커뮤니티·브랜딩)인데 브랜딩은 커뮤니티를 import 할 수 없어서, 서비스에서 순서대로 지우면
    한쪽 문만 고쳐진다. 엔티티에도 `@OnDelete(action = CASCADE)` 를 같이 달아야 한다 —
    **테스트는 H2 + hbm2ddl 이라 V19 를 읽지 않는다.**
14. **삭제·수정 관문 쿼리에는 `showOnProfile` 을 건다(브랜딩 쪽).** 안 걸면 커뮤니티 전용 글을
    브랜딩 엔드포인트로 편집할 수 있고, 브랜딩 수정은 카테고리 규칙을 몰라 **같이가요 글에 강의를
    연결하는 우회로**가 된다. **반대로 커뮤니티 관문(`CommunityPostJpaRepo.findMine`)에는 걸지 않는다** —
    통합 폼·숨김 토글은 프로필 글이든 커뮤니티 전용 글이든 다뤄야 한다.
15. **어드민이 조치(ACTIONED)한 글은 작성자가 숨김을 되돌릴 수 없다.** 숨김의 주인이 둘인데 컬럼이
    하나라, 막지 않으면 토글 한 번으로 조치가 무효가 된다.
16. **UNIQUE 로 멱등을 만들 때 제약 위반을 같은 트랜잭션에서 잡으면 안 된다.** 잡아도 트랜잭션이
    rollback-only 라 뒤이은 조회·커밋이 터진다 — 삽입만 `IdempotentInsert`(REQUIRES_NEW + flush)로
    격리하고 바깥에서 잡는다. **그 뒤의 카운트도 새 트랜잭션에서 읽는다**(`IdempotentInsert.countFresh`) —
    MySQL 기본 REPEATABLE READ 에선 바깥 트랜잭션이 첫 SELECT 시점 스냅샷을 끝까지 봐서, REQUIRES_NEW 로
    커밋한 행이 바깥의 `count` 에 안 잡힌다(POST 응답 count 가 "내 것 빠진 값"이던 2026-08-17 버그).
    H2 는 기본 READ COMMITTED 라 이걸 못 잡는다 — 재현 테스트는 `CommunityReactionCountUseCaseTest` 가
    자기 컨텍스트만 격리 수준을 올려서 잠근다(전역으로 올리면 H2 2.1 의 CASCADE 삭제 NPE 가 난다).
    **원리·패턴 메뉴·체크리스트의 단일 출처는 [docs/architecture/transactions.md](../../../../../../../docs/architecture/transactions.md)** —
    enrollment(H-4)·payment(원장) 가 먼저 밟은 같은 함정이다.

17. **"내가 쓴 글"(`GET /community/posts/me`) 은 숨김의 회수 경로다.** 오너 브랜딩 그리드는 프로필 글만,
    피드는 숨김을 뺀다 — 이 목록이 없으면 `숨김 + 커뮤니티 전용` 글은 상세 URL 로만 닿는다.
    카드에 `hidden`·`showOnProfile` 을 함께 실어야 FE 가 뱃지·토글을 그린다. 시큐리티 매처는
    리터럴이라 `/community/posts/*` permitAll **앞**에 둔다(뒤에 두면 비로그인이 컨트롤러까지 와서 500).

18. **인기 순위식은 `CommunityPostJpaRepo.ENGAGEMENT_SCORE` 하나다** — 인기순 피드(전체·카테고리)와
    트렌딩 토픽이 공유한다. 갈라놓으면 같은 화면에서 "인기 탭 1등 ≠ 지금 뜨는 토픽 1등" 이 된다.
    ⚠️ 세 축을 한 번에 조인하므로 **`count(distinct 자식.id)` 가 필수**다. 그냥 `count()` 면 카티전 곱
    (좋아요 10 × 댓글 5 × 북마크 3 = 150행)이 그대로 점수가 된다. 삭제 댓글은 `on` 절에서 뺀다 —
    카드의 `commentCount` 와 기준이 갈리면 "댓글 3인데 점수엔 5" 다.
19. **태그 정규화는 `BrandingPostTag.normalize` 하나를 두 쓰기 경로가 쓴다**(커뮤니티·구 브랜딩).
    한쪽만 고치면 그쪽으로 들어온 태그가 집계를 오염시키고, 인기 태그 목록만 봐서는 어느 쪽인지 알 수 없다.
    하는 일은 공백·선행 `#` 제거, 빈 값 버림, 같은 글 안 중복 제거뿐 — **대소문자는 통일하지 않는다**
    (`OW`→`ow` 는 표기를 망치고 한글엔 실익이 없다). 거부가 아니라 교정이라 DTO 가 아니라 여기 있다.
20. **집계 창이 두 개다.** 인기순·토픽·카테고리 카운트는 **7일**, 인기 태그는 **30일**(`TAG_WINDOW_DAYS`).
    통일하고 싶어지겠지만 태그는 글보다 성기게 쌓여서 7일이면 사이드바가 통째로 비고, 창을 없애면
    초기 태그가 영구히 상단에 굳는다.

## `validate` 가 잡아주지 않는 것 (스키마 작업 시 주의)

- **`hbm2ddl=validate` 는 테이블·컬럼의 *존재*와 타입 정도만 본다.** 컬럼 **길이**(varchar(60) vs (100)),
  **nullable**, **인덱스**, **FK 의 ON DELETE 규칙**은 검증하지 않는다. 즉 V19 와 엔티티가 이 축에서
  어긋나도 부팅은 성공하고, 런타임에 데이터가 잘리거나(길이) FK 위반(삭제)으로 드러난다.
  → 마이그레이션을 고칠 때 **엔티티와 SQL 을 나란히 놓고 눈으로 대조**할 것.
- **N+1 없음은 `hibernate.default_batch_fetch_size: 100` 에 기대고 있는 부분이 있다.** 이 값을 낮추거나
  지우면 일괄 조회로 짠 곳들이 조용히 느려진다(에러가 아니라 쿼리 수만 는다).
