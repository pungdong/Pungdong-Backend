# 게시물의 두 표면 — 커뮤니티 피드 ↔ 브랜딩 그리드 (post-surfaces)

> **피처 문서** — 두 화면의 **관계 정책·왜·히스토리를 소유**한다. 구현(ER·엔드포인트·권한 매트릭스)은
> [architecture/community.md](../architecture/community.md) · [architecture/branding.md](../architecture/branding.md) 로 링크만 한다.
> 각 화면 고유 정책은 [features/community.md](community.md) · [features/account-branding.md](account-branding.md).

## 한 줄

**게시물은 행 하나이고 화면이 둘이다** — 커뮤니티 피드(*흐름*)와 브랜딩 프로필 그리드(*하이라이트*).
작성자는 글을 하나 쓰고 "내 프로필에도 남길지"만 고른다.

## 이 문서가 따로 있는 이유 (먼저 읽을 것)

두 화면의 관계가 **비대칭**이라, 한쪽 도메인만 보고 작업하면 **반드시 틀린다.** 실제로 세 번 밟았다:

| 밟은 것 | 무슨 일이 났나 |
|---|---|
| 공유 테이블에 노출 축(`show_on_profile`)을 더함 | 브랜딩의 **기존 쿼리 3개가 조용히 틀렸다** — 커뮤니티 글이 프로필 그리드로 새고 헤더 통계가 타일 수와 어긋남 |
| 숨김 엔드포인트를 두 도메인에 각각 둠 | 한쪽은 커뮤니티 전용 글을 못 숨겼고, 다른 한쪽은 **어드민 조치를 작성자가 되살리는 우회로**였다 |
| FE 가 `category == null` 로 "브랜딩발 글"을 판정 | 컬럼이 NOT NULL 이 되는 순간 판정 자체가 소멸 — 계약 문서에 **틀린 안내가 남아 있었다**(#285 에서 정정) |

공통 원인은 하나다: **테이블은 branding 이 소유하는데 쓰기 규칙은 community 가 소유한다.**
그래서 "이 테이블을 읽고 쓰는 경로 전체 목록"을 먼저 만들지 않으면 항상 한쪽만 고치게 된다.

## 협력 도메인

| 도메인 | 구현 문서 | 이 관계에서의 역할 |
|---|---|---|
| branding | [architecture/branding.md](../architecture/branding.md) | **테이블·엔티티 소유**(`branding_post` / `BrandingPost`), 프로필 그리드·고정·프로필 공개 여부 |
| community | [architecture/community.md](../architecture/community.md) | **쓰기·숨김·반응·신고 규칙 소유**, 피드 조회 |
| account | — | 작성자(계정당 `account_branding` 1행 UNIQUE) — 이 유일성이 "글 ↔ 프로필 = 0..1" 의 근거 |
| course | [architecture/course.md](../architecture/course.md) | 연결 강의(두 표면 공통) |

**의존 방향은 community → branding 단방향**이다. branding 은 community 를 import 하지 않는다 —
그래서 브랜딩 쪽에서 커뮤니티 규칙(신고 조치·카테고리 가드)을 확인할 수 없고, 그게 아래 "문은 하나"
규칙의 실질적 이유다.

## 모델 — 행 하나, 표면 둘, 상태 셋

노출을 정하는 컬럼은 둘이다: `is_hidden`(전역 스위치) · `show_on_profile`(더하기).

| `isHidden` | `showOnProfile` | 커뮤니티 피드 | 브랜딩 그리드 | 오너 본인 |
|---|---|---|---|---|
| false | false | 보임 | 안 보임 | 보임 (피드 · 내가 쓴 글) |
| false | true | 보임 | 보임 | 보임 (+ 오너 그리드) |
| true | false | 안 보임 | 안 보임 | **내가 쓴 글**에 숨김 표시 + 상세 |
| true | true | 안 보임 | 안 보임 | **오너 그리드**에 숨김 표시 + 상세 |

→ 표현 가능한 공개 상태는 **셋뿐**이다: ①커뮤니티만 ②커뮤니티+프로필 ③숨김.
**"브랜딩 전용"(커뮤니티엔 안 뜨는 프로필 글)은 만들 수 없고, 이건 의도한 제약이다.**
프로필은 *더하기*이고, 커뮤니티 노출을 끄는 수단은 숨김 하나뿐이다.

> `show_in_feed` 컬럼이 아직 있지만 **모든 쓰기 경로가 1 로 쓴다**(V31 에서 남아 있던 0 행도 정리).
> "프로필 전용" 이 언젠가 필요해지면 되살릴 자리이고, 피드 인덱스의 선두 컬럼이라 지우지 않았다.
> 지금 이 값을 0 으로 만드는 코드를 새로 쓰면 위 진리표가 깨진다 — 화면이 설명하지 못하는 네 번째 상태가 된다.

**왜 테이블이 하나인가**: `account_branding` 은 계정당 1행이고 글의 작성자는 1명이라 "글 ↔ 프로필" 은
항상 0..1 이다. 맵핑 테이블은 조인 하나 늘어난 boolean 이고, 테이블을 쪼개면 그리드가 UNION 이 되어
정렬·페이징·`totalElements` 가 얹히고 좋아요·댓글·신고가 폴리모픽 FK 로 빠진다. 상세는
[architecture/community.md](../architecture/community.md).

## 정책

### 1. 작성 폼은 하나, 프로필 노출은 작성자가 고른다 🔴

`POST|PUT /community/posts` 하나로 쓰고, `showOnProfile`(기본 false)이 프로필 그리드 노출을 결정한다.

- **스냅샷이다** — `mediaUrls`·`tags` 와 같은 규칙이라 PUT 에서 빠지면 `false` 로 읽혀 **프로필에서 내려간다.**
  클라이언트는 상세 응답의 값을 그대로 되실어야 한다.
- **프로필에서 내리기 ≠ 삭제**: 글·좋아요·댓글은 그대로 남고 커뮤니티에는 계속 보인다.
- **사진 0장이면 켤 수 없다**(400) — 그리드는 사진 타일이라 썸네일 없는 글이 빈 칸이 된다.
- 구 `POST|PUT /branding/me/posts` 는 **구버전 앱 호환**으로만 남는다. 거기로 온 글은 `showOnProfile=true`
  고정. **여기에 필드를 더하기 전에 통합 폼으로 되는 일인지 먼저 확인할 것.**

**왜 이 방향인가**: 반대(브랜딩 요청에 카테고리·제목을 더해 두 엔드포인트 유지)로 가면 같은 폼이 분기해
두 계약을 부르고, 필드가 하나 늘 때마다 양쪽을 고쳐야 한다. 테이블이 하나라 서버 비용은 플래그 하나다.

### 2. 숨김은 전역 스위치이고, 문도 하나다 🔴

컬럼이 하나라 **어느 화면에서 켜든 두 표면에서 함께 빠지고, 어디서 풀든 함께 돌아온다.**
토글 경로는 **`PATCH /community/posts/{id}/visibility` 하나** — 브랜딩 쪽 쌍둥이는 삭제했다.

문을 하나로 줄인 이유는 대칭성이 아니라 **규칙이 실제로 갈렸기 때문**이다:
브랜딩 경로는 (a) `show_on_profile=true` 인 글만 통과시켜 커뮤니티 전용 글을 못 숨겼고,
(b) **어드민 조치(`ACTIONED`) 확인이 없어 신고로 내려간 글을 작성자가 되살릴 수 있었다.**
(b) 를 브랜딩 쪽에서 고칠 수 없는 건 단방향 의존 때문이다(branding 은 `content_report` 를 못 읽는다).

→ **여기에 두 번째 숨김 경로를 만들지 말 것.** 만들면 같은 우회로가 다시 생긴다.

### 3. 두 축은 직교한다 🔴

- 숨김을 풀어도 **프로필로 승격되지 않는다**: `(T,F)` → 풀기 → `(F,F)`.
- 프로필에 올려도 **숨김이 풀리지 않는다**: `(T,F)` → 승격 → `(T,T)` (남에겐 계속 안 보임).

FE 와 합의한 TC 표(H-1~H-6 · P-1~P-4 · C-1~C-3 · Q-1~Q-5)는 `CommunityUseCaseTest` 의 `P*` 그룹
주석에 매핑돼 있고 전부 테스트로 잠겨 있다. **이 두 축을 건드리는 변경은 그 그룹을 먼저 읽을 것.**

### 4. 오너에게는 언제나 되돌릴 화면이 있어야 한다 🔴

"안 보임" 은 **남에게만**이다. 오너 화면에서도 사라지면 그건 숨김이 아니라 삭제다.

| 글 | 오너의 회수 경로 |
|---|---|
| 프로필 글(`showOnProfile=true`) | 브랜딩 오너 그리드 `GET /branding/me/posts` (숨김 포함) |
| 그 외 전부 | **`GET /community/posts/me`** (숨김·프로필 미노출 포함) |

`/community/posts/me` 가 없던 동안 `숨김 + 커뮤니티 전용` 글은 **어느 목록에도 없어 상세 URL 로만**
닿았다. 새 노출 축을 더할 때는 "이 상태의 글을 오너가 어느 목록에서 보나"를 같이 답해야 한다.

### 5. 소유권 분할 — 무엇을 어느 도메인이 정하나

| 결정 | 소유 | 비고 |
|---|---|---|
| 테이블·엔티티·미디어/태그 자식 행 | **branding** | 이름이 `branding_post` 인 이유는 아래 "함정" |
| 그리드 정렬·상단 고정(`pinned`) | **branding** | 고정은 **프로필 전용 개념** — 피드 정렬에 영향 없음 |
| 프로필 공개 여부(`is_published`) | **branding** | 아래 "네 번째 축" |
| 작성·수정·삭제 규칙(카테고리·제목·MATCH 강의연결 가드·CDN URL) | **community** | 통합 폼이 규칙의 단일 지점 |
| 숨김 토글 + 어드민 조치 락 | **community** | 문 하나 |
| 좋아요·북마크·댓글·신고 | **community** | 자식 행은 DB `ON DELETE CASCADE` 로 정리(삭제 문이 둘이라) |

## 자주 틀리는 것 (작업 전 체크리스트)

1. **`branding_post` / `BrandingPost` 라는 이름은 실수가 아니다.** ECS 롤링 중 구버전 태스크가 살아 있어
   RENAME 이 돌면 그 태스크가 없는 테이블을 조회해 **브랜딩 페이지가 500** 이 된다. 이름은 내부 구현,
   경로가 계약이다.
2. **관문 쿼리의 비대칭은 의도다.** 브랜딩 `findMine` 은 `show_on_profile=true` 를 **요구하고**,
   커뮤니티 `findMine` 은 **보지 않는다.** 전자는 커뮤니티 전용 글이 카테고리 규칙을 모르는 문으로
   들어오는 걸 막고, 후자는 통합 폼·숨김이 모든 글을 다뤄야 하기 때문. 한쪽에 맞춰 통일하면 둘 중
   하나가 깨진다.
3. **`category == null` 로 "브랜딩발 글"을 판정하던 규칙은 소멸했다**(V31 부터 `category`·`title` NOT NULL).
   그런 글은 더 이상 없고, **모든 글이 커뮤니티 PUT 대상**이다. 옛 판정을 되살리지 말 것.
4. **`is_published` 라는 네 번째 축이 있다.** 프로필을 비공개로 돌리면 `showOnProfile=true` 여도
   **공개 그리드 진입 자체가 400** 이다. 반면 커뮤니티 피드에는 계속 뜬다 — 포트폴리오 비공개가
   커뮤니티 발언을 지우지는 않는다는 의도된 조합이고, 카드에서 작성자를 누르면 프로필이 400 인
   상태가 정상이다(클라이언트가 graceful 처리).
5. **삭제 문이 둘이다**(커뮤니티·브랜딩). 자식 행은 서비스가 아니라 **DB `ON DELETE CASCADE**` 로
   정리한다 — 서비스에서 지우면 한쪽 문만 고쳐진다. 엔티티에도 `@OnDelete` 를 같이 단다
   (테스트는 H2 + hbm2ddl 이라 마이그레이션을 안 읽는다).
6. **새 노출 축을 더할 땐 이 테이블을 읽는 경로 목록을 먼저 만든다** — 피드/그리드(공개·오너)/상세
   ×2/통계/집계/관문 쿼리. 이 문서 맨 위 표의 첫 사고가 그걸 안 해서 났다.

## 미해결 / 확장

- 🟡 **상세 URL 이 둘이다** — `GET /community/posts/{id}` 와 `GET /branding-posts/{id}`. 후자는
  프로필 글만 열고 커뮤니티 전용 글은 오너에게도 닫는다. 통합 폼이 자리 잡으면 하나로 줄일 여지.
- 🟡 **`pinned` 는 프로필 전용**이라 피드 정렬과 무관하다. 피드에 고정 개념을 넣자는 요구가 오면
  같은 컬럼을 재사용하지 말 것 — 두 화면의 정렬 의미가 달라진다.
- 🟢 **`show_in_feed` 는 상수 true** (위 모델 섹션 주석).
- 🟡 **글의 위치를 참조로**(`venueRefId`) — FE 요청 보류 중. 이 레포의 위치 참조는 숫자가 아니라
  문자열 토큰 `"CUSTOM:<pk>" | "OFFICIAL:<sanityId>"` 이고, **CUSTOM 위치는 강사 비공개**라 공개 글에
  이름이 노출되는 문제를 먼저 정해야 한다(후보: 글에는 OFFICIAL 만 허용, 나머지는 `locationLabel`).
  [features/venue.md](venue.md) 참조.
