# 닉네임 (nickname)

> 여러 도메인(account · branding · moderation)에 걸친 **교차 피처**. 이 문서는 *정책·왜·결정 히스토리*를 소유한다. 구현(형식 규칙표·판정 위치·응답 필드)은 [docs/architecture/sign-up.md](../architecture/sign-up.md) "닉네임 정책".

## 한 줄

닉네임은 **표시명이자 공개 URL 식별자**(`/instructors/{nickName}`)라, 자유 입력이 아니라 **형식 가드 + 예약어 차단**이 걸린 값이다 — 라우트 충돌·사칭·공식 이름 선점 세 가지를 동시에 막는다.

## 협력 도메인

| 도메인 | 역할 | 구현 문서 |
|---|---|---|
| `account` | 닉네임 소유(가입·변경·중복확인) · 형식/예약어/중복 판정 | [sign-up.md](../architecture/sign-up.md) |
| `branding` | 닉네임을 **공개 URL 식별자로 소비**(`GET /instructors/{nickName}`) — 라우트 리터럴과의 충돌이 여기서 발생 | [branding.md](../architecture/branding.md) |
| `moderation` | 사후 경로(신고). **사칭 사유가 아직 없다** — 아래 미해결 | [moderation.md](moderation.md) |
| `global/validation` | `NickNamePolicy` — 형식·예약어·정규화 **단일 출처** | — |

## 정책

### 닉네임은 URL 식별자다 — 그래서 좁다

브랜딩 D3 결정으로 공개 프로필의 URL 키가 순차 id 가 아니라 닉네임이 됐다([account-branding.md](account-branding.md)). **자유 표시명이면 안 걸릴 제약이 그 결정의 귀결로 따라온다**:

| 걸리는 것 | 안 막으면 |
|---|---|
| 라우트 충돌 | Spring 은 리터럴을 path variable 보다 우선한다 → 닉네임이 `public`·`suggested` 인 계정의 프로필이 **영영 안 열린다** |
| 사칭 | `풍덩공식`·`우리동네관리자` 가 플랫폼/운영자 행세를 한다. 다이빙은 안전이 걸린 도메인이라 **운영자를 사칭한 안내**의 무게가 다르다 |
| 선점 | 우리가 나중에 진짜 공식 계정을 만들 때 쓸 이름이 남아 있어야 한다 |

### 방어는 3층이고, 문자셋이 그 중 절반이다

형식(문자셋·길이) → 예약어 → 중복. **문자셋을 좁히는 게 사칭 방어의 절반**이라는 게 이 피처의 핵심 통찰이다 — 한글(완성형)·영문·숫자·밑줄만 남기면 동형이의 문자(키릴 `а` vs 라틴 `a`)·제로폭 문자·이모지·공백이 **원천 차단**된다. 예약어 목록은 *아는 단어*만 막지만, 문자셋은 *목록이 모르는 우회*를 통째로 닫는다. 반대로 문자셋이 열려 있으면 예약어를 아무리 늘려도 `аdmin` 하나에 뚫린다.

### 예약어 매칭은 하나로 통일하지 않는다

언어마다 단어 경계가 다르기 때문에 **한 가지 매칭으로 하면 반드시 어딘가 틀린다**.

| 매칭 | 대상 | 왜 |
|---|---|---|
| **포함** | 브랜드(`풍덩`·`pungdong`·`plop`), 한글 역할어(`관리자`·`운영자`·`고객센터`…) | 한글은 단어 경계가 없다 — `우리동네관리자` 를 정확일치로는 못 잡는다 |
| **정확일치·접두** | 라틴 역할어(`admin`·`official`·`support`…) | 부분일치로 하면 `badminton` 이 `admin` 에 걸린다 |
| **정확일치** | 라우트어(`public`·`suggested`·`me`·`api`…)·시스템어·한글 단독어(`공식`·`운영`…) | 부분일치의 오탐이 이득보다 크다 |

**오탐은 차단 실패보다 비싸다는 판단**을 한 곳에서 실제로 했다 — `master` 는 접두 차단 목록에서 뺐다. `masterdiver` 는 실제 다이빙 등급 표기라, 이걸 막으면 **멀쩡한 강사가 자기 등급을 못 쓴다**. 단독 `master` 만 막는다. (같은 이유로 라틴 역할어 전체가 접두 매칭이다.)

판정 전 **정규화**(대소문자·구분자 제거·NFKC·리트 치환)를 거치므로 `p_u_n_g_d0ng` 같은 우회는 접혀서 걸린다. 이 정규화 값은 **판정 전용**이고 표시·저장에 쓰지 않는다.

### 어드민은 예약어 예외 — 정책이 자기 목적을 배반하지 않게

`ROLE_ADMIN` 은 예약어 가드를 건너뛴다. **막아 둔 목적 자체가 "우리가 나중에 쓰려고"** 인데 정작 우리가 못 쓰면 선점의 의미가 없다. 단 **형식 가드는 어드민에게도 적용**된다 — URL 식별자라는 사실은 계정 권한과 무관하다(`풍덩 공식` 은 어드민도 못 쓴다, 공백 때문에).

### "쓸 수 없음" 은 에러가 아니라 답이다

중복확인(`GET /sign/check/nickName`)은 형식 위반·예약어도 **200 + `{available, reason}`** 으로 답한다(레포 API 규칙: check/query 는 반환, guard 는 throw). 여기서 놓치기 쉬운 함정 하나 — **형식 위반·예약어는 아무도 안 쓰므로 `exists:false`** 다. `exists` 만 보면 FE 가 초록불을 켜 놓고 가입에서 400 을 맞는다. 그래서 `exists`(호환 유지)와 별개로 `available` 이 최종 판정이다.

### 무엇을 알려주고 무엇을 숨기는가 (비대칭)

- **형식 오류는 무엇이 왜 틀렸는지 그대로** 알려준다. 형식 규칙은 이미 공개 계약(`types.ts`·FE)이고 서버 상태에 의존하지 않아 **oracle 이 아니다** — 숨겨서 얻는 보안이 없고, 숨기면 사용자가 고칠 수가 없다.
- **예약어는 어떤 단어인지 알려주지 않는다.** 목록은 공개 계약이 아니라 **운영 정책**이라 계속 늘어나고, 노출하면 그대로 우회 사전이 된다. (`"사용할 수 없는 닉네임입니다."` 한 문장으로 고정.)

### 소급 적용하지 않는다

이 규칙은 **가입·변경 시점**에만 걸린다. 이미 예약어/형식 위반 닉네임을 가진 계정은 그대로 둔다 — **유저에게 보이는 식별자를 서버가 임의로 바꾸는 건 별개의 작업**이고(공유 링크·검색·대화 맥락이 전부 그 이름에 묶여 있다), 강제 변경은 개별 안내가 선행돼야 한다. 탐지는 `account/audit` 이 부팅 로그(`[nickname-audit]`)로 리포트하고, **판정은 가입 차단과 같은 `NickNamePolicy`** 를 쓴다(리포트와 차단 규칙이 갈리면 진단으로 못 쓴다).

### 사전 차단은 사후 신고와 짝이다

목록 기반 차단은 **아는 단어만** 막는다. `풍덩` 을 안 쓰면서 사칭하는 이름(`공식파트너`·`대표강사` 류)은 사람이 보고 신고해야 잡힌다. 즉 이 피처는 [moderation](moderation.md) 의 신고 경로와 한 쌍인데, **현재 `ReportReason` 에 사칭 사유가 없다** — 아래 미해결.

## 미해결 / 확장

- 🔴 **`account.nick_name` UNIQUE 인덱스 부재** — 공개 URL 식별자인데 DB 유일성이 없다. 중복 dedupe 는 유저에게 보이는 이름을 바꾸는 작업이라 실데이터 점검·승인 후 별도 마이그레이션. (이 PR 로 audit 판정이 차단 규칙과 일치해져 사전 점검의 정확도는 올라갔다.) → [account-branding.md](account-branding.md) 미해결
- 🟡 **`ReportReason.IMPERSONATION` 부재** — 사전 차단의 짝인 사후 경로가 비어 있다. FE 신고 시트에 노출되는 값이라 제품 결정이 선행. → [moderation.md](moderation.md)
- 🟡 **기존 예약어 보유 계정 안내** — `public`·`suggested` 보유자는 지금도 프로필이 안 열린다. prod 부팅 로그 `[nickname-audit]` 확인 후 개별 안내 필요(자동 변경 안 함).
- ⚪ **예약어 추가는 배포가 필요하다** — 목록이 코드 상수라 운영 중 추가하려면 배포해야 한다. 빈도가 높아지면 Sanity/DB 로 옮기는 걸 검토(지금은 빈도가 낮아 코드가 단순해서 이득).
- ⚪ **하이픈(`-`) 미허용** — URL 안전하고 핸들 관행이지만 우선 밑줄만 열었다. 요청이 오면 재검토(정규화가 구분자를 지우므로 예약어 방어는 약해지지 않는다).
- ⚪ **문자셋이 한국 종속이다** — 완성형 한글 + 라틴만 받으므로 일본 확장 시 히라가나/가타카나/한자(그리고 그때의 사칭 단어)를 열어야 한다. **글로벌화 인벤토리 항목**(추상화하지 말고 목록화 — 나중에 문자 범위를 넓히는 건 UPDATE 없이 규칙 변경만으로 되므로 지금 미리 하지 않는다). → 이슈 [#173](https://github.com/pungdong/Pungdong-Backend/issues/173)

## 관련 메모리

- `feedback_validate_input_shape` — 입력은 형식(shape)까지 검증. 형식 오류 메시지 노출이 안전한 이유(oracle 판별)가 이 피처의 "무엇을 알려주는가" 비대칭과 같은 논리
- `globalization_when_to_abstract` — 지금 추상화할 것 vs 목록화할 것. 닉네임 문자셋은 **목록화** 쪽
- `region_grouping_policy` — 라벨이 규칙을 감추면 사용자가 오해한다는 같은 계열의 교훈
