# 세션 단체 채팅 (session group chat)

> **무엇을 / 왜.** 구현(엔드포인트·ER·쿼리)은 [chat 패키지 CLAUDE.md](../../src/main/java/com/diving/pungdong/chat/CLAUDE.md), 알림 파이프라인은 [architecture/notification.md](../architecture/notification.md), 일정 도메인은 [architecture/availability.md](../architecture/availability.md).
>
> 걸치는 도메인: `chat`(신규) · `availability`(일정) · `enrollment`(참여 자격) · `notification`(푸시) · `account`(표시명). 작성 2026-08-16.

## 1. 무엇을 만들었나

강사의 **가용시간 슬롯(일정, `AvailabilitySession`) 하나 = 단체 채팅방 하나.** 그 슬롯에 결제를 마친 수강생들과 강사가 한 방에서 대화한다.

진입은 두 곳이고, **채팅만 모아보는 목록 화면은 만들지 않았다**:

| 진입점 | 화면 |
|---|---|
| 강사 "내 일정 > 슬롯 상세" 의 **세션 단체 채팅** CTA | `AvailabilitySessionResponse.chat` |
| 수강관리(강사)·강의일정(학생) **회차 카드의 채팅 버튼** | `InstructorRoundCard.chat` / `ScheduleRound.chat` |

메시지를 보내면 **발신자를 뺀 참여자 전원에게 푸시**가 간다.

## 2. 왜 "일정"이 채팅의 단위인가

수강 관리는 **사람 1명의 수강 기록**을 보는 곳이라 대화의 허브가 아니다. 반면 같은 (위치, 시간블록) 슬롯에는 **여러 수강생의 회차가 join** 된다(`AvailabilitySession` 의 정체성 = `(instructor, date, venueRefId, startTime, endTime)`). 그날 그 시간에 물리적으로 같이 모이는 사람들 = 대화가 필요한 단위다. 그래서 그룹의 키가 일정이다.

따라서 **`roundId` 는 방 키가 될 수 없다** — 회차 : 일정 = N : 1 이라 같은 방에 여러 `roundId` 가 매달린다.

## 3. 결정과 근거

### 3-1. 🔴 방은 일정에 FK 를 걸지 않는다

`availability.SessionCleaner` 는 **"session 존재 ⟺ 점유 > 0"** 불변식을 지키느라 점유가 0 이 되면 일정 행을 **물리 삭제**한다. 결제한 수강생이 전원 취소·환불하면 실제로 일어난다.

여기에 FK 를 걸면 그 삭제가 제약 위반으로 실패해 **환불 플로우가 깨진다** — 결제 하드닝으로 막 굳혀 놓은 경로다. 그래서 방의 PK 를 일정 id 로 두되 **FK 는 걸지 않았다**(선례: `user_notification.recipient_account_id`).

얻은 것:
- `SessionCleaner` **무변경** — 채팅 때문에 손댈 곳이 없다
- 일정이 사라져도 방·메시지가 남아 **옛 푸시 딥링크가 계속 열린다**(CLOSED 읽기 전용)
- 방 행이 없어도 `roomId` 를 알 수 있어 **목록 조회가 방을 만들지 않는다**

안전성 근거는 **MySQL 8.4**(prod RDS·로컬 동일)가 AUTO_INCREMENT 를 영속하고 삭제된 id 를 재사용하지 않는다는 것 — 한 번 쓰인 일정 id 가 다른 일정에 다시 붙지 않으므로 옛 방과 새 방이 충돌하지 않는다. 같은 슬롯이 지워졌다 다시 생기면 **새 id → 새 방**이고 옛 방은 CLOSED 로 남는다.

### 3-2. 방은 결제 시점이 아니라 **처음 열 때** 만든다

`PaymentCompletedEvent` 를 들으면 결제 코드를 건드리지 않고 방을 미리 만들 수 있어 매력적이었다. **기각했다** — `PaymentService.publishPaymentCompleted` javadoc 이 경고한다:

> 알림 리스너는 결제 트랜잭션에 합류하므로 여기서 실패하면 **승인된 결제가 롤백**된다 — 알림 때문에 결제가 깨지면 안 된다.

리스너는 `@Transactional(MANDATORY)` 다. 방 생성이 던지면 승인된 결제가 날아간다. 지연 생성은 결제·환불 write path 를 전혀 건드리지 않는다.

### 3-3. 참여 자격 = 결제 완료 = `{ACCEPT_PENDING, CONFIRMED}`

디자인이 "결제 전 = 미생성" 이라고 정했다. 이 도메인은 **선결제**라 결제가 강사 수락보다 **먼저** 일어나고, **미결제 상태는 `PENDING` 하나뿐**이다. `ACCEPT_PENDING` 은 "결제완료·강사 결정 대기" 이므로 참여자에 **포함**된다 (`RoundScheduleStatus.from` 이 `PENDING → PAYMENT_DUE`, `ACCEPT_PENDING → WAITING` 으로 매핑하는 것이 근거).

`REJECTED`/`CANCELLED` 는 자동환불된 상태라 자동으로 빠진다.

### 3-4. 방 수명 = 결제 완료 ~ **세션 종료 + 24h**

종료 후에도 하루를 더 여는 건 수업 직후의 정산·후기·분실물 같은 대화가 남기 때문이다. 마감 뒤에는 **읽기 전용**("회차 채팅이 종료됐어요") — 조회는 계속 200 이고 전송만 막힌다. 지난 대화를 지우면 CS 근거가 사라진다.

슬롯 시각(`date`+`endTime`)은 오프셋 없는 **civil** 값이라 그대로는 타임라인 위의 점이 아니다. 마감 판정은 절대시각 비교라 존이 필요한데 `venue.timeZone` 이 아직 없어(일본 확장과 한 몸으로 미뤄짐) **KST 고정**이다 — `payment.RefundService` 가 환불율 기준일에 같은 선택을 한 것과 같다.

### 3-5. 딥링크가 **채팅방으로 직행**한다 (규약 정정)

기존 알림은 파라미터 없는 **허브로 착지**한다. 처음엔 이걸 "강한 규약" 으로 보고 예외를 요청했는데, 사용자 판단은 **규약 정정**이었다 — 허브 착지는 v1 에 그 화면들이 **없었기 때문**이지 원칙이 아니었다. 채팅은 목록 메뉴 자체가 없어서 방으로 못 가면 알림이 쓸모없다. 착지 실패 시 폴백만 허브로 둔다.

### 3-6. 전송은 멱등이다 (`clientMessageId` 필수)

응답이 유실된 뒤 사용자가 다시 누르면 중복 메시지가 남는다. FE 의 "자동 재시도 금지" 로는 **수동 재전송**을 막을 수 없고, 나중에 넣으려면 스키마 변경 + 백필이라 처음부터 넣었다(결제 하드닝에서 세운 멱등 원칙과 같은 결).

중복이면 **에러가 아니라 기존 메시지를 200** 으로 돌려주고(신규는 201), **푸시를 재발행하지 않는다** — 재시도 한 번에 참여자 전원이 알림을 두 번 받으면 안 된다.

⚠️ **UUID 포맷을 강제하지 않는다.** RN(Hermes)에 WebCrypto 가 없어 강제하면 모바일에 네이티브 의존성 2개 + pod install 이 따라붙는다. UNIQUE 가 `(보낸사람, 키)` 라 사용자 간 충돌은 무의미하고, 한 사용자의 짧은 재시도 창에서만 유일하면 충분하다.

### 3-7. 실시간은 폴링 + 푸시 (WebSocket·SSE 기각)

인프라가 롱커넥션에 적대적이다:

| 사실 | 함의 |
|---|---|
| WS/SSE/STOMP/reactive 코드·의존성 **0** | 셋 다 신규 비용이 같다 — 기존 투자가 어느 쪽도 밀어주지 않는다 |
| ALB `idle_timeout` 미설정 = 기본 **60초** | 롱커넥션은 하트비트 또는 Terraform 변경이 **강제**된다 |
| `desired_count=1` + rolling 30초 드레인 | **매 배포가 커넥션을 끊는다** |
| target group stickiness **없음** | 나중에 태스크를 2로 올리면 WS/SSE 가 조용히 깨진다 |
| 커넥션 단위 관측 수단 **없음** | 롱커넥션 헬스를 볼 방법이 없다 |

반면 푸시는 요구사항상 **어차피 만들어야 한다.** 만들고 나면 폴링은 커서 GET 하나가 전부다. 화면이 열려 있는 동안만 `?after=` 로 폴링(권장 3초, 백오프 자유)하고 백그라운드는 FCM 이다.

**되돌릴 수 있는 결정이다** — API 가 커서 기반이라 나중에 SSE 를 얹어도 클라이언트 상태 모델이 그대로다.

### 3-8. 표시명은 BE 가 합성한다

`displayName`("김수민 학생")을 서버가 만들어 내린다. FE 합성으로 두면 web/mobile **사본 2벌**이 갈라지는데, 이 레포에서 반복적으로 어긋나 온 부류다(`display.ts`·`postTime.ts`·`certData.ts` 가 전부 "두 파일을 같이 고칠 것" 주석을 달고 있다). 자격증 트랙에서 세운 "표시명은 BE 스냅샷" 원칙과 같다.

`mine`(말풍선 좌우)도 같은 이유로 서버가 계산한다 — 클라이언트가 자기 `accountId` 를 아는 경로가 플랫폼마다 달라 판정 버그가 나기 쉽다.

## 4. v1 에 넣지 않은 것

| 항목 | 왜 |
|---|---|
| **첨부·이미지** | 텍스트 전용으로 시작. `[+]` 버튼은 숨긴다. 인프라(`S3Uploader`+`ImageUploadPolicy`)는 있으니 필요할 때 붙인다 — 지금 `content_type` 같은 컬럼을 미리 두지 않는다 |
| **메시지 신고** | 커뮤니티 `ContentReport` 패턴을 복사하면 되지만 v1 범위 밖. 앱스토어 UGC 정책상 필요해질 수 있어 백로그 1순위 |
| **채팅 목록 화면** | "따로 뺄 이유가 없다" — 진입은 일정·수강관리 두 곳으로 충분 |
| **per-room 알림 mute** | `notification_preference` 신설이 필요한 별도 인프라 |
| **사용자 차단/뮤트** | 레포 전체에 인프라가 없다 |
| **메시지 삭제 API** | `deleted` 컬럼과 툼스톤 문구만 두고 경로는 안 만들었다 |

**레이트리밋은 최소 가드만** 넣었다 — 최근 10초 10건 초과 시 429(`-1023`) + `retryAfterSeconds`. 범용 레이트리밋 인프라가 레포에 없고(유일 선례는 본인확인 OTP 의 Redis 쿨다운), 커뮤니티도 미구현으로 남아 있다. 대형 인프라를 새로 짓지 않는다는 판단이다.

## 5. 운영에서 알아야 할 것

- 🔴 **prod 는 `FIREBASE_ENABLED=false` 라 실제 푸시가 무음이다.** outbox 는 `SENT` 로 기록돼 정상처럼 보인다. 이 트랙과 **분리**해 알림 트랙의 묶음 배포에서 켠다 — 켜기 전까지 "메시지 → 푸시" 요구사항은 prod 에서 동작하지 않는다.
- **웹에는 푸시가 없다**(설계상 제외). 다만 outbox 행과 알림함 행을 같은 트랜잭션에 함께 쓰므로 **웹 알림센터에는 자동으로 쌓인다** — 추가 작업이 없다.
- **없음/비참여 = HTTP 400 + code `-1009`** 다(404 아님 — 이 레포의 `ResourceNotFoundException` 매핑). FE 딥링크 폴백은 status 가 아니라 **code** 로 분기해야 한다.
- 메시지 1건 = 참여자 N명 × (outbox 1 + 알림함 1) insert + N×토큰수 FCM 호출이다. 기본 정원이 4명이라 지금은 무해하지만, 정원이 커지면 재검토 대상이다.

## 6. 관례에서 벗어난 두 가지 (의도적, 승인됨)

| 이탈 | 왜 |
|---|---|
| **커서 페이지네이션** (다른 목록은 전부 `Pageable`+`PagedModel`) | 채팅은 append-heavy 라 새 메시지가 들어오면 offset 페이지가 밀려 과거 스크롤에서 중복·누락이 난다 |
| **assigned PK** (다른 엔티티는 예외 없이 `IDENTITY`) | 방의 정체성이 곧 일정이고, 방 행이 없어도 `roomId` 를 알아야 목록 조회가 쓰기를 하지 않는다 (§3-1) |

둘 다 [chat 패키지 CLAUDE.md](../../src/main/java/com/diving/pungdong/chat/CLAUDE.md) 에 근거를 적어 뒀다.

## 7. 알려진 인접 결함 (이 피처가 만든 것 아님)

`EnrollmentService.mySchedule` 은 회차에 `venueRefId` 가 **하나도 없으면** `resolveNames` 가 `Map.of()` 를 돌려주고 거기에 `get(null)` 을 해 **NPE(500)** 가 난다. 위치 없는 회차만 가진 학생이 강의일정을 열면 재현된다. 채팅과 무관해 이번 PR 에서 건드리지 않았고, `ChatUseCaseTest` 는 픽스처에 `venueRefId` 를 채워 피해 간다.
